# Phase 2 A1 alert architecture

Status: implemented and verified locally; live team credentials and screen integration remain
required for the final gate.

## Channel authority

The central screen is the primary channel. A1 persists the alert and publishes canonical
`ward/alert` JSON before attempting the Telegram backup. A Telegram, roster or waveform failure
does not close or downgrade the screen alert. Delivery outcomes are published separately as
`ward/action` records.

High alerts (`EMERGENCY`, `BOTH` and `patient_not_ok`) notify the assigned nurse immediately.
Step 2 adds the next nurse after 30 seconds in `demo` or 60 seconds in `design-real`. Step 3 adds
all unit nurses and the on-call doctor after the same interval. `AlertMessage.to` is cumulative,
while Telegram sends only to recipients newly introduced by the step. Medium and low alerts
notify the assigned nurse once without a timed ladder. `DEVICE_ATTACK` remains outside the nurse
alert path.

## Durable state

PostgreSQL stores one active alert per bed, callback idempotency receipts, opaque Telegram
callback targets, per-recipient delivery state and the last authenticated roster snapshot.
APScheduler stores only the alert ID and expected next step. When a job fires, the coordinator
reloads current alert state before acting, so a cancelled, acknowledged or already-advanced job
has no effect.

Screen alerts, A1 action events and Telegram bedside results enter the existing PostgreSQL
outbox before MQTT delivery. Broker failures retry with bounded backoff, while stable delivery
keys make alert-state replays safe for the backend to upsert.

Every Telegram send and edit, ladder escalation and acknowledgement produces a `ward/action`
outcome. A Telegram failure changes its delivery record to `failed`; it never changes the
clinical alert status to `failed`.

One process-level transition lock serializes alert mutations in the datathon service. Database
uniqueness additionally prevents more than one active alert per bed. The supported deployment is
one Uvicorn worker and one APScheduler leader.

## Live integration contract

The automation service calls the authenticated backend endpoints:

- `GET /internal/v1/ward/assignments/{bed_id}` for assigned nurse, next nurse, unit nurses and
  on-call doctor;
- `GET /internal/v1/beds/{bed_id}/waveform-snapshot?end_ts=&seconds=12` for a PNG attachment.

The backend forwards screen actions to:

- `POST /internal/v1/alerts/{alert_id}/ack`;
- `POST /internal/v1/alerts/{alert_id}/escalate`.

Both commands require the backend bearer token and an idempotent `event_id`. Telegram callback
tokens are random, opaque and persisted. The sender identity comes from the protected
staff-to-chat mapping rather than callback data.

Successful command responses preserve the canonical `alert` object and legacy `summary`, and add
an `outputs` object:

- `outputs.user`: short clinical wording without staff identifiers;
- `outputs.team`: deterministic operational line with alert identity, recipients and state;
- `outputs.model`: the unchanged locked v1 JSON object.

The human lines are sanitized, one physical line and at most 160 characters. The model object is
authoritative; no component parses either human line to make a decision.

## Alert lifecycle

- Repeated five-second verdicts update the stable active alert text, reasons and delivery state.
- A priority increase upgrades that alert; a lower-priority repeat cannot downgrade it.
- `On my way` records response milliseconds, stops timers and edits every delivered copy.
- `Patient OK` acknowledges and closes the active event.
- `Patient NOT OK` creates or upgrades a high alert and leaves its ladder active.
- `NORMAL` never cancels an unacknowledged alert. It closes the event boundary only after an
  acknowledgement.
- Manual escalation advances one level and schedules the following level from that moment.
- Completed duplicate callbacks return stored state without repeating finalization effects.

## Safe failure behavior

- No current roster: publish the screen alert with an empty recipient list and mark phone routing
  unavailable. Use a cached roster only while its shift validity has not expired.
- Waveform unavailable: send text and buttons.
- Telegram unavailable or identity missing: retain the screen alert and publish a failed A1
  `send_message` action.
- Unknown, stale, repeated or unauthorized callbacks cannot change alert state.
- No operational alert text is generated by Granite and no Phase 2 action can control treatment.
